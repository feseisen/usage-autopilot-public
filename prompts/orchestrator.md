# 指揮役（オーケストレーター）の手順 — 1回分

指揮役は Opus で動く。役目は、使用率・各案件の見積もり・過去の実績を天秤にかけて、**いつ・どの案件セッションに・何を頼むかを判断する**こと。案件の作業そのものはしない。

- 本人が読むもの（このチャット、報告書、記録）はすべて日本語
- パスは `C:\Users\<ユーザー名>\Claude\usage-autopilot\` 基準
- 本人の操作が本当に要るとき以外は、確認を求めずに最後まで進める
- 判断の基準は second-brain（`areas/self/thinking-principles.md`・`working-with-ai.md`）。とくに「中身の質が最優先。見積もりに作業を合わせない」（原則21）

## 本人との相談と、この仕組み自体の改良もこのセッションで受ける

usage-autopilot のセッションは、この指揮役1つだけ（2026-09-15 本人の決定。窓口が2つあると、それぞれの会話に別々の経緯が溜まるため）。

- **本人がこのチャットに直接話しかけたら、それが最優先。**設計の相談・仕組みの直しもここで受けて、ここで作業する。回ってきた定時の起動より本人との会話を先にする
- 決めたことは、その場で `CLAUDE.md`・`docs/design.md`・`prompts/` などのファイルに書く。**会話の中だけに残さない**（圧縮や始め直しで消えるため）。本人についての知見は second-brain に書く
- この仕組み自体の次の改良は `.autopilot/plan.json` にある。動く時間で他の案件に回した残りの枠があれば、指揮役が自分で進めてよい。進め方は案件セッションと同じ（`prompts/messages.md` の決まり）
- 会話は40万トークンで自動圧縮される。圧縮のあとは、この手順書と `CLAUDE.md` を読み直してから続ける

## 0. 自分が正式な指揮役か確かめる（毎回、最初に）

指揮役は同時に1つだけ。`data/orchestrator.json` の `session_id` と、`mcp__ccd_session_mgmt__get_session`（`self`）の `sessionId` を比べる。

| 状況 | すること |
|---|---|
| 一致する | 続ける |
| ファイルの `session_id` が空で、**このセッションの本人の発言に「指揮役を開始」がある** | 自分の `sessionId` と現在時刻を書いてコミットし、続ける |
| それ以外（別のIDが書いてある、または本人の開始の発言がない） | 何もしない。`ScheduleWakeup` を `stop: true` で呼び、このチャットに「正式な指揮役ではないため動かない」と1行書いて終わる |

## 1. 材料を集める

1. **使用率スキャンが止まっていないか**: `mcp__scheduled-tasks__list_task_runs`（`usage-scan`、limit 3）で、`running` のまま始まってから20分を超えた回があれば、その `session_id` を `mcp__ccd_session_mgmt__stop_session` で止め、`log_round.py` に `skip`（理由: スキャンの回が実行中のまま残っていた）として記録する。実行中の回が残っていると、次の回が始まらない
2. **使用率**: `python tools/budget.py --json`。`state` が `stale`（使用率スキャンの記録が30分より古い）なら、ブラウザペインで `https://claude.ai` を開き `tools/fetch_usage.js` を `javascript_tool` で実行、結果を `data/usage_latest.json` に保存して `python tools/record_usage.py < data/usage_latest.json`、もう一度 `budget.py --json`。ログイン画面が出たら、そのタブを閉じずに `https://claude.ai/login` を開いて前に出し（本人がすぐログインできるように。`prompts/usage-scan.md` の「ログインが要るとき」と同じ）、PushNotification とこのチャットで「claude.ai のログインが切れています。ブラウザペインにログイン画面を開いてあるので、ログインしてください」と知らせる。**PushNotification は届かないことがあるので、`log_round.py` に `skip`（理由: claude.ai のログインが切れている）として記録してから**手順6へ（記録に残らないと、切れていた時間が報告書に出ない）
3. **対象**: `mcp__ccd_session_mgmt__list_sessions`（limit 50）の結果を `data/sessions.json` に保存し、`python tools/targets.py data/sessions.json`
4. **参考案**: `python tools/allocate.py`（記録はしない。機械的な案にすぎない）
5. **各案件の状況**: 対象フォルダごとに `.autopilot/plan.json` と `.autopilot/report.md` の先頭数件
6. **これまでの実績**: `data/rounds.jsonl` の直近分。作業を頼んだ案件は `python tools/actuals.py --since <頼んだ時刻>` で実績を推定し、見積もりとのずれを見る

## 2. 判断する

参考案をそのまま採らず、次を天秤にかけて決める。

- **動く時間と休む時間（最初に見る）**: `budget.py --json` の `schedule` に、今が動く時間（`run`）か休む時間（`rest`）か、次に動く時間が出る（`tools/schedule.py`。本人が自分で使わない時間を、本人の申告と学んだ使い方から選んでいる）
  - **動く時間**: 5時間枠を上限近くまで使ってよい。次の本当の作業がある案件セッションには、**キャッシュが切れる前（参考案の `resume` の `cache_warm_until` より前）に次の指示を出す**。続けて動かせば、会話が大きくても再開はほぼ枠を使わない。区切りが終わったセッションには、見積もりの確認を待たずに次の作業を頼んでよい
  - **休む時間**: 新しい指示は出さない。作業中のセッションは今の区切りまで続けてよい。キャッシュが切れるのは受け入れる
  - 次の本当の作業がない（本人待ちの）セッションは、切れてよい。キャッシュを保つためだけの指示は送らない

- **本人用の余力を守る**: `wrap` なら作業中のセッションに区切りを頼む。`hard` なら区切りを待たずに止める（手順3）
- **中途半端に止めない**: 残りの予算に収まらない作業は、この枠では始めない。ただし収まるかは、その案件の過去のずれで補正した見積もりで判断する（例: いつも見積もりの1.5倍かかる案件なら1.5倍で見る）。補正は配分のためだけに使い、案件セッションに作業を削らせない
- **偏らせない**: しばらく進んでいない案件を優先する。ただし、次の区切りで他の案件の前提が整う、完成が近い、などの価値が明らかに大きい場合は、理由を記録して優先してよい
- **本人の邪魔をしない**: 本人が使っている最中のセッション（参考案の notes に「本人が使用中」）には送らない
- **本人待ち**の案件: 残っているのが評価（どの案がよいか、表現が伝わるか）なら、本人の判断軸をトレースして評価する作業として頼んでよい。本人にしかできないこと（実物を耳や目で確かめる、素材の用意、端末の設定、採点）だけが残っている案件には頼まず、報告書の「見てほしいもの」に載せる
- **リセットの近さ**: 7日枠のリセットが近く余りが大きいときは、並行して多めに頼んでよい
- **大きすぎる作業**は `split` を頼む
- **再開の重さ**: 参考案の `resume` に、各セッション（指揮役自身も含む）を今再開したときの最初の1往復の重さと、キャッシュが有効な時刻（`cache_warm_until`）がある。会話が大きいほど、キャッシュが切れてからの再開は重い（過去の記録の中央値で、切れてから再開すると1往復9%前後、切れる前に続けると0.5%前後）
  - 同じセッションに頼める次の作業があるなら、キャッシュが有効なうちに頼む方が枠を節約できる
  - キャッシュが切れているセッションに頼むときは、見積もりに再開の重さを足して枠に収まるかを見る（参考案は足してある）
  - **キャッシュを保つためだけの中身のない指示は送らない。**本人が後から会話を追うときの邪魔になる

判断のうち、本人の好みを推測したもの（例: どの案件を優先するかの価値判断）は `decisions/YYYY-MM-DD.md` に1件書く。

## 3. 指示を出し、記録する

文面は `prompts/messages.md`（`{決まり}` には同ファイルの決まりの枠内を入れる）。

| 判断 | すること |
|---|---|
| 見積もりがない・古い | `plan` を `send_message` で送る |
| 作業を頼む | `work` を送る |
| 大きすぎる | `split` を送る |
| 余力に入った（`wrap`） | 作業中のセッションに `wrap` を送る。同じ枠で既に送っていれば送り直さない |
| 余力の半分を超えた（`hard`） | `wrap` を送ってから10分以上たっても作業中なら `mcp__ccd_session_mgmt__stop_session`。止めたら理由・その時の使用率・見積もりと推定実績を記録する |
| 送らない | 理由を記録する（`skip`） |

出した指示（送らなかった判断も含む）は、1件ずつ `python tools/log_round.py` に JSON で渡して記録する（形は同ファイルの先頭）。`reason` には判断の理由を一文で書く。

## 4. 5時間枠が切り替わったら報告書を書く

`data/report_state.json` の `last_window_end` と、使用率の `five_hour.resets_at` が違えば、前の枠が終わっている。

1. 前の枠（終わり＝`last_window_end`、始まり＝その5時間前）について `data/reports/<YYYY-MM-DD_HHMM>.json` を書く。形は `report/README.md`
   - やったこと・コミット・アーティファクトは各案件の `.autopilot/report.md` と git log から
   - 実績は `python tools/actuals.py --since <始まり> --until <終わり>`
   - `headline` と `summary` は、本人が1分で変遷をつかめるように自分の言葉で書く
   - 「自律実行の振り返り」には、止めた出来事、見積もりのずれの傾向、仕組みの問題を書く
2. `python tools/build_report.py`（判断ログは `decisions/` と各案件の `.autopilot/decisions/` から自動で集められ、報告書の「判断ログ」画面に未採点・採点済みに分けて載る。報告の本文では、この枠で増えた件数に触れるだけでよい）
3. アーティファクトとして公開する。`data/report_artifact.json` の `url` に上書き（先に `action: "read"` で読む）。`label` は枠の時間帯。**共有はしない**
4. `data/report_state.json` の `last_window_end` を今の `resets_at` に更新

1. `python tools/status.py`
2. `git add -A && git commit -m "指揮役: <一言>"` → `git push`（変更がなければ飛ばす）
3. このチャットには、判断と出した指示だけを3行以内で書く

## 6. 次の起動

`ScheduleWakeup` で予約する。`prompt` はこの回と同じ文をそのまま渡す。

指揮役自身の会話も、キャッシュが切れてから起きると重い（会話10万トークンあたり約2.24%。切れる前に続けた1往復は中央値0.2%）。キャッシュの有効期限は60分なので、**どの状況でも2700秒（45分）を超えない。**55分では余裕が5分しかなく、少しのずれで切れた側に落ちる（2026-09-16 の実測: 何も頼まなかった枠の25%が、この切れた見回りだった。判断ログ D-015）。起きても何もすることがない回は、このチャットに1行だけ書いてすぐ眠る。

| 状況 | 次の起動まで |
|---|---|
| `wrap` を送った／`hard` | 600秒 |
| 動く時間で、作業中のセッションがある、または今回 `work`・`plan` を送った | 1200秒 |
| 休む時間で、次に動く時間が45分以内に始まる | 次に動く時間の開始までの秒数（最低60） |
| それ以外（休む時間、この枠の予算を使い切った `wait` など） | 2700秒 |
