# 設計: 余った枠で、各案件のセッションを並行して進める

## 1. 全体の形

**本人が各セッションで「続けてください」と言っていたことを、代わりに行う仕組み。**作業そのものは各案件の既存のセッションが行い、この仕組みは「いつ・どのセッションに・どれだけ進めさせるか」だけを決める。

| 役割 | どこで動くか | モデル | やること |
|---|---|---|---|
| **使用率スキャン** | 定期タスク（30分ごと） | 軽いモデル | 使用率を取って記録するだけ |
| **指揮役** | usage-autopilot の専用セッション（1つ） | Opus | 予算・見積もり・過去の実績を天秤にかけて配分を判断、各セッションへの指示、見張り、5時間枠ごとの報告書 |
| **案件セッション** | 各リポジトリの既存のセッション | Opus | 次の区切りを決める、使う量を見積もる、区切りまで進める、見える形に残す |

**案件の中身についての判断は、すべて案件セッションが行う。**指揮役は、どの案件にどれだけ枠を回すかを判断する。配分は複数の材料を天秤にかける取捨選択なので、指揮役も Opus で動かす。

### 技術的な前提（2026-09-13 に確認）

- 普通のチャットセッションからは、他のセッションにメッセージを送って作業を始めさせられる。止めることもできる
- 定期実行（ルーティン）のセッションからは、他のセッションに送れない。**だから指揮役は定期実行ではなく、開いたままのチャットセッションにする**
- 指揮役の時間ごとの起動は、そのセッション内の繰り返し実行（`/loop`）で行う。指揮役は同時に1つだけで、本人が「指揮役を開始」と明示したセッションだけが動く（`data/orchestrator.json`）。**アプリを閉じる・PCが眠ると止まる**

## 2. 対象のセッションの見つけ方

案件の数は固定しない。指揮役は毎回、次の規則で対象を選び直す。

1. アプリのセッション一覧から、`C:\Users\<ユーザー名>\Claude\` 直下のフォルダごとに、**アーカイブされていない最新のセッション**を1つ選ぶ
2. 定期実行が作ったセッションは除く
3. `targets.md` の「外すフォルダ」は除く。初期値は次のとおり
   - `second-brain` — 全セッションの前提になるため、自動では動かさない
   - 指揮役のセッション自身は、どのフォルダでも対象にしない（`data/orchestrator.json`）
   - 使うセッションを固定したいフォルダは、`targets.md` の「使うセッション」に書く

新しい案件のリポジトリができれば、次の回から自動で対象に入る。

## 3. 進め方 — 区切りの単位で配分する

**途中で止めない。**「区切りまでの作業」を単位にして、その見積もりで配分する。

```
[見積もり] 各案件セッション: 「次の区切りまでに何をするか」と「使う量の見積もり」を書く
     ↓
[配分]     指揮役: 予算・見積もり・過去のずれを天秤にかけて、この5時間枠で進める案件を決める
     ↓
[実行]     案件セッション: 区切りまで進める（質を優先し、見積もりに合わせて作業を削らない）
     ↓
[記録]     案件セッション: 成果を見える形に残し、次の区切りと見積もりを書く ← 次の[見積もり]を兼ねる
```

### 見積もり

- 最初の1回だけ、指揮役が各セッションに「次の区切りと見積もりだけ書いて止まって」と頼む。見積もるだけなら使う量は小さい
- 以後は、各セッションが区切りを終えるたびに次の見積もりを書くので、見積もりのための起動は要らない
- 書く場所: 各案件のリポジトリの `.autopilot/plan.json`（作業内容の一文、見積もり＝5時間枠の何%か、本人の評価待ちかどうか）。案件セッションが自分のフォルダの外を読み書きしないで済むようにするため

### 配分

1. この5時間枠の予算（→ 4章）を出す
2. **しばらく進んでいない案件から順に**並べる（1つだけが進んで他が止まる状態を避ける）
3. 見積もりが残り予算に収まる案件から指示を出す。**収まらない案件は、この枠では始めない**（始めると途中で止まるため）。大きすぎて、どの枠にも収まらない案件には、区切りを小さく分けるよう頼む
4. 本人の評価待ちの案件は飛ばす

### 見張り

- 使用率は30分ごとの定期タスクが記録し、指揮役は作業中のセッションがあれば20分おき、区切りを頼んだ後は10分おきに見る
- 見積もりを超えても、区切りまでは続けさせる
- 5時間枠が本人用のバッファに入ったら、作業中のセッションに「区切りをつけて止まって」と送る。メッセージは作業の途中でも読まれるので、近い区切りで止まってもらえる
- それでも止まらず、バッファの半分まで食い込んだら、指揮役がセッションを止める（usage-autopilot の設定で許可済み）。止めた出来事は理由と使用率を記録し、報告書で見積もりとのずれと合わせて振り返る

### 見積もりの精度を上げる

- 公式の使用率は全セッションの合計しか分からない
- 案件ごとの実際の量は、このPCの会話記録のトークン量を、公式の使用率で当てはめた係数で5時間枠%に換算して推定する（`tools/actuals.py`・`tools/calibration.py`）
- 案件ごとに「見積もり」と「実績」を記録し、ずれ方を次の見積もりに反映する

## 4. 配分 — 動く時間にまとめて使い、休む時間は休む

### 動く時間と休む時間（2026-09-15 本人の決定）

- **7日枠を使い切ればよく、すべての5時間枠を使う必要はない。**動く時間は5時間枠を上限近くまで続けて使い、休む時間は何も頼まない
- 理由: 会話はキャッシュが生きている間はほとんど枠を使わない（60万トークンの会話でも読み込みは約0.01%）が、60分以上あけると書き直しで約14%かかる。薄く毎枠に配ると休みが1時間を超えて毎回切れる。まとめて動かせば、切れるのは動くまとまりの始まりだけになる
- 動く時間の中では、次の本当の作業があるセッションに、キャッシュが切れる前に次を頼む。次の作業がないセッションは切れてよい（中身のない指示は本人が会話を追えなくなるので送らない）
- **どこで動くかは、本人が自分で使わない時間から選ぶ**（`tools/schedule.py`）。本人の申告（`data/user_rhythm.json`、例: 平日の午前2時〜7時は寝ている）と、会話記録から学んだ本人の使い方を合わせて、本人が使いそうな量が少ない5時間のまとまりから、7日枠の残りを使い切るのに足りる分だけ選ぶ。記録が少ないうちは、申告の無い時間を控えめに「使いそう」とみなす
- 判定は仮置き。本人の実際の使い方との照合を重ねて詰める
- 5時間枠は、枠が切れたあとの最初の利用から始まる（記録上、リセット時刻が 17:00 の次は 22:10 になっている）。使用率スキャンが30分ごとに動くため、枠は途切れずにつながる


### 段階

本人の使用の予測は、記録が少ないうちは精度が出ない。精度の低い予測で配分すると、それ自体が配分を歪める。そこで2段階で進める。

| 段階 | 配分 | 移る条件 |
|---|---|---|
| **1. 仮置き（今）** | 動く時間は上記の選び方。本人用に7日枠・5時間枠とも20%を残し（今から5時間枠のリセットまでずっと申告の空き時間なら5時間枠は残さない）、7日枠はリセットの48時間前から、5時間枠はリセットの2時間前から0%へ減らす（`tools/budget.py`）。同時に、本人の使用と自律実行の使用を切り分けた履歴を溜める | — |
| **2. 予測** | 下の「計算の流れ」 | 溜めた履歴で予測を試算し、実際の本人の使用とのずれが仮置きの20%より小さくなったら |

段階1の間も、報告書には「予測していたら何%残したか」と「実際に本人が使った量」を並べて載せ、移る判断の材料にする。

### 考え方

- **本人用の余力は、固定の割合ではない。**「この先、本人が自分で Claude を使いそうな量」で決まり、曜日や時間帯で変わる（本人は土日が休みで、土日に多く触る）
- **7日枠はリセット間際にまとめては使えない。**5時間枠1つで使える量に上限があるので、使い切るには残りの5時間枠の回数から逆算して、前倒しで配る必要がある。たとえば土曜の時点で、残りの枠を全部使っても余る見込みなら、もう余力を減らしてよい
- **予測は外れる前提。**本人の実際の使い方と予測のずれを枠ごとに記録し、次の予測に反映する（原則21）

### 計算の流れ（段階2。水を注ぐ配り方は、動く時間の中の配分に使う）

1. **本人の使い方の予測（U）**: 過去の記録から、曜日の種類（平日・土日）と時間帯ごとに、本人が5時間枠を何%使うかを出す。同じ種類の日の同じ時間帯のうち、多く使った側（上位25%）の量を「残しておくべき量」とする。記録が少ないうちは下限を置く
2. **自律実行が各5時間枠で使える量（C）**: 7日枠のリセットまでに回ってくる5時間枠ごとに、`C = (100 − その枠で予測される本人の使用量) × その時間帯にアプリが開いている見込み`
3. **自律実行が7日枠で使える量（B）**: `B = 100 − 今の7日枠の使用率 − リセットまでに予測される本人の使用量`（5時間枠%で表すと B × r）
4. **前倒しの配り方**: 各枠に同じ高さまで水を注ぐように配る。`Σ min(C, 水位) = B × r` となる水位を求め、今の枠には `min(今の枠の C, 水位)` を配る
   - 残りの枠の C を全部足しても B × r に届かない（＝7日枠が使い切れない）なら、水位は上限なしになり、各枠は C まで使う。リセットが近づくと自然にこうなる
   - 7日枠に対して枠の数が十分あるなら、水位が各枠の使用を抑え、週全体に均等に配る
5. **今の枠の上限** = `min(100 − この枠の残り時間で予測される本人の使用量, この枠の本人の予測使用量 + 配った量)`

### 使う記録

| 記録 | 何に使うか | 置き場所 |
|---|---|---|
| 公式の使用率（30分ごと） | 5時間枠%と7日枠%の実測、アプリが開いていた時間帯 | `data/usage_snapshots.jsonl` |
| 会話記録のトークン量 | 本人の使用と自律実行の使用の切り分け。他のセッションからのメッセージや定期タスクで始まった作業は自律実行、それ以外は本人 | `~/.claude/projects/`（Claude Code が古いものを消すことがあるため、時間帯ごとに集計して `data/usage_history.jsonl` に保存し続ける） |
| r（7日枠1%あたりの5時間枠%） | 2つの枠の換算 | 同じ週の中で続けて取れた使用率の記録をつなげて出す（5時間枠をまたぐ区間は係数で換算）。2026-09-13 時点で10.0（7日枠26%分から） |
| 稼働率 | 残りの5時間枠の数を実際に合わせる | 使用率の記録か会話記録の応答がある1時間を「開いていた」と数える。72時間観測するまでは 1.0 |
| トークン量→5時間枠%の係数 | 会話記録の量を枠の%に換算する | 公式の使用率の増え方と、同じ区間のトークン量から当てはめる（`tools/calibration.py`）。キャッシュ書き込みと出力が枠を使い、読み込みはほぼ使わない |

### 限界

- claude.ai のチャットや他の端末での利用は会話記録に無い。公式の使用率の増え方と自律実行の推定分の差を「本人の使用」とみなして補う
- 記録は 2026-08-23 以降の9日分しかない。しばらくは下限の余力に頼る

## 5. 見える形に残す

本人が空いた時間に覗いたとき「今こうなっているのか」が分かることを、区切りの条件に含める。

- 各案件セッションは、区切りのたびに次を更新する
  - その案件の `CLAUDE.md` の「現在地」
  - その案件の成果物（非公開のアーティファクトを含む）
  - そのセッションのチャットに、日本語で短い報告
- 本人に聞かずに決めたことは、判断ログ（`decisions/`）に書く。本人が採点する
- 指揮役は5時間枠が切り替わるたびに報告書を書き、非公開のアーティファクトに上書きで公開する。過去の回はページ左の一覧からワンタッチで開ける（`report/README.md`）

## 6. この設計の弱いところ

- **見積もりは粗い。**同じ「区切りまで」でも、使う量は数倍ぶれる。実績との差を記録して、次の見積もりと配分に活かす
- **r（7日枠と5時間枠の比）と稼働率は、使用率スキャンが止まらずに動いていることが前提。**スキャンが止まると、どちらも精度が落ちる
- **使用率の取得は、claude.ai が画面表示のために使っている非公開の仕組みに頼っている。**予告なく変わる可能性がある。取れなくなったら指揮役は全セッションを止めて本人に知らせる
- **指揮役（Opus）と使用率スキャンも枠を使う。**計算はスクリプトに任せ、指揮役自身の消費は報告書に載せて見直す
- **並行するセッションが同時に second-brain に書くと、git がぶつかる。**書き込みは区切りの最後にまとめ、失敗したら少し待って再試行する
- 夜間など、アプリが開いていない時間は動かない。稼働率はその前提で記録から出す
